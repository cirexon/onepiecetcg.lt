# Production readiness checklist

**Release rule:** every applicable row must pass before production launch; an item may be marked `N/A` only when the reason, reviewer, and review date are recorded in the release evidence.

**Evidence format:** record `PASS`, `FAIL`, or `N/A`, the tester, UTC timestamp, environment or commit SHA, and a link or path to the report, screenshot, log, or decision.

## 1. Security & Privacy

| ID | Check | Standard or tool | Pass | Fail |
| --- | --- | --- | --- | --- |
| SEC-01 | Force every request to HTTPS and redirect HTTP without mixed content. | SSL Labs, browser Security panel, `curl -I` | TLS is valid, HTTP redirects once to HTTPS, and no page loads insecure subresources. | Any certificate error, HTTP content, redirect loop, or mixed-content warning exists. |
| SEC-02 | Send a reviewed security-header policy on every HTML response. | OWASP Secure Headers, Mozilla Observatory, SecurityHeaders.com | CSP or CSP report-only rollout is documented, and HSTS, `X-Content-Type-Options`, clickjacking protection, `Referrer-Policy`, and `Permissions-Policy` have expected values. | A required header is missing, malformed, overly permissive without approval, or inconsistent across routes. |
| SEC-03 | Keep credentials, private keys, access tokens, and service-account files out of source, build output, logs, and Git history. | GitHub secret scanning, Gitleaks or TruffleHog, manual `dist` inspection | Scans return no verified secret and all local secret files are ignored by Git. | A usable secret appears anywhere in the repository, artifact, client bundle, or log. |
| SEC-04 | Confirm browser configuration contains only publishable Firebase identifiers and never privileged credentials. | Firebase web setup documentation, bundle search | The built JavaScript contains no service-account key, admin SDK credential, refresh token, or private API credential. | Any privileged credential is shipped to the browser. |
| SEC-05 | Block production releases with known high or critical runtime dependency vulnerabilities. | `npm audit --omit=dev --audit-level=high`, OSV Scanner | The production dependency scan reports zero unresolved high or critical findings. | Any unresolved high or critical runtime finding remains. |
| SEC-06 | Review development-tool vulnerabilities separately and document exposure and mitigation. | Full `npm audit`, GitHub Advisory Database | Every high or critical dev-only finding has an owner, exposure decision, mitigation, and review date. | A dev-tool finding is ignored, mislabeled as production risk, or lacks a decision. |
| SEC-07 | Restrict Firebase Authentication to approved providers, support email, and authorized production domains. | Firebase Console → Authentication | Only intended providers and exact localhost, Firebase, and custom domains are enabled. | An unused provider or unauthorized domain is enabled, or a required production domain is absent. |
| SEC-08 | Enforce least privilege in Firestore rules independently of hidden buttons or client routing. | Firebase Rules Emulator, OWASP ASVS v5 access-control requirements | Visitor, Organiser, Editor, Administrator, and Owner tests all allow only their documented operations. | Any role can read or write data outside its permission layer. |
| SEC-09 | Prevent horizontal access attacks against drafts, results, account data, and organiser-owned events. | Rules Emulator IDOR tests, OWASP ASVS v5 | Cross-account reads and writes fail for every tested object identifier. | Changing a document ID or route grants access to another user’s protected data. |
| SEC-10 | Prevent vertical privilege escalation and protect the Owner role. | Rules Emulator role-escalation tests | Users cannot change themselves, Administrators cannot change Administrators or Owners, only the Owner can grant Administrator, and no client can grant Owner. | Any client path permits self-promotion, peer-admin changes, Owner creation, or Owner demotion. |
| SEC-11 | Validate document shape, types, ranges, ownership, and allowed values at the database boundary. | Firestore Rules Emulator, boundary-value tests | Valid minimum and maximum records pass while missing, extra, malformed, and out-of-range fields fail. | The database accepts unbounded, malformed, unexpected, or owner-swapped data. |
| SEC-12 | Render untrusted text without executable HTML, JavaScript URLs, or unsafe DOM sinks. | OWASP ASVS v5, DOM Invader, code search for `dangerouslySetInnerHTML` | Stored and reflected payloads display as text and no unsafe sink receives user-controlled content. | Any payload executes script, injects markup, or reaches an unreviewed unsafe sink. |
| SEC-13 | Protect authentication sessions and logout behavior. | Browser storage inspection, Firebase Auth tests | Tokens use Firebase-managed storage, logout invalidates local access, protected data disappears after logout, and no token enters logs or URLs. | Protected access persists after logout or a credential leaks through storage, logs, referrers, or URLs. |
| SEC-14 | Verify CSRF and state-changing request protections for every write path. | OWASP ASVS v5, browser network inspection | Writes require an authenticated Firebase SDK request accepted by Firestore rules, with no unauthenticated state-changing endpoint. | A cross-origin or unauthenticated request can change application data. |
| SEC-15 | Restrict API keys and service access to the intended Firebase project, APIs, and domains where supported. | Google Cloud Console → Credentials, Firebase documentation | Key restrictions and API restrictions are applied where compatible, and exceptions are documented. | A key can call unrelated APIs or is unrestricted without a reviewed reason. |
| SEC-16 | Limit automated abuse and quota exhaustion on authentication and database operations. | Firebase App Check evaluation, Firebase Usage dashboards, abuse test | App Check is enforced where feasible or a documented compensating control, quota alert, and response threshold exists. | Anonymous automation can consume material quota with no detection or response control. |
| SEC-17 | Return safe user-facing errors without stack traces, internal paths, tokens, emails, or raw provider responses. | OWASP ZAP, browser console/network review | Expected and forced failures show a generic actionable message while sensitive diagnostics stay out of the client. | An error exposes sensitive implementation or personal information. |
| SEC-18 | Keep production logs and audit records minimal, access-controlled, and free of secrets. | Firebase/Google Cloud log review, GDPR data-minimization review | Log fields, viewers, retention, and redaction are documented and sampled logs contain no credential or unnecessary personal data. | Logs expose secrets or excessive personal data, or access and retention are undefined. |
| SEC-19 | Run an automated baseline attack scan against the deployed release candidate. | OWASP ZAP Baseline Scan | The scan has no unresolved high-risk alert and every medium-risk alert has a documented disposition. | A high-risk alert remains or a medium-risk alert has no owner and decision. |
| SEC-20 | Confirm third-party links and new tabs cannot control the opener or leak unnecessary referrer data. | DOM inspection, browser test | Every untrusted `target="_blank"` link uses `noopener` or `noreferrer`, and the site referrer policy matches the privacy decision. | An external page receives opener access or more referrer data than approved. |
| SEC-21 | Verify unavailable features such as uploads, payments, messaging, and password authentication are genuinely absent. | Architecture review, route and network inventory | Each non-feature is documented as absent and exposes no dormant endpoint, SDK, bucket, or provider. | An undocumented or unused attack surface remains enabled. |
| SEC-22 | Define security ownership, vulnerability intake, patch urgency, and incident escalation before launch. | OWASP ASVS governance, incident-response runbook | Named owners and deadlines exist for critical, high, medium, and low findings, with a tested contact path. | Findings can arrive without an owner, deadline, or escalation route. |

## 2. Documentation & Compliance

| ID | Check | Standard or tool | Pass | Fail |
| --- | --- | --- | --- | --- |
| DOC-01 | Maintain a data inventory covering source, purpose, fields, visibility, storage location, recipients, and retention. | GDPR Articles 5 and 30, data-flow diagram | Every personal-data field, including login email, public player name, city, UID, and audit metadata, is mapped. | Personal data exists outside the inventory or lacks purpose, owner, or retention. |
| DOC-02 | Record a lawful basis and purpose for every personal-data operation. | GDPR Article 6, Lithuanian State Data Protection Inspectorate guidance | Each processing purpose has one documented lawful basis approved by the data owner. | A purpose has no basis, uses incompatible purposes, or relies on assumed consent. |
| DOC-03 | Publish a clear privacy notice at or before personal-data collection. | GDPR Articles 12–14 | The notice identifies the controller, contact, purposes, bases, recipients, transfers, retention, rights, complaint route, and automated decision status. | Required information is missing, inaccurate, hidden, or delivered after collection. |
| DOC-04 | Obtain and retain a defensible basis for publishing player names, cities, profiles, and tournament history. | GDPR Articles 5–7, consent record when consent is used | Every public player record has documented permission or another recorded basis, with a correction and removal route. | A person can be published without a recorded basis or usable removal process. |
| DOC-05 | Collect only data required for community results and administration. | GDPR Article 5(1)(c), privacy review | Every field has a current purpose and unused fields or providers are removed. | Any field is collected “just in case” or has no active purpose. |
| DOC-06 | Define retention periods and implement deletion or anonymization for accounts, role history, player profiles, events, logs, and backups. | GDPR Article 5(1)(e), retention schedule | Each data class has a trigger, period, action, owner, and tested execution method. | Data is retained indefinitely without a documented need or cannot be deleted. |
| DOC-07 | Document and test requests for access, correction, deletion, restriction, objection, and data portability where applicable. | GDPR Articles 15–22 | A test request can be authenticated, tracked, completed, and evidenced within the legal deadline. | A right cannot be exercised, verified, or completed on time. |
| DOC-08 | Document processors and sign or accept appropriate data-processing terms. | GDPR Article 28, Google Cloud/Firebase Data Processing Addendum | Each processor is listed with purpose, contract/DPA, security role, and owner. | A processor handles personal data without documented terms or review. |
| DOC-09 | Assess international transfers and record the transfer mechanism and supplementary measures where needed. | GDPR Chapter V, EDPB guidance | Every non-EEA transfer is identified and supported by an applicable mechanism or confirmed absent. | A transfer exists with no valid mechanism or assessment. |
| DOC-10 | Inventory cookies, IndexedDB, local storage, authentication storage, analytics, and embedded third-party requests. | EU ePrivacy rules, browser Application and Network panels | Every client-side storage item and third-party request has purpose, lifetime, provider, and consent classification. | Undocumented tracking, storage, or third-party requests occur. |
| DOC-11 | Obtain consent before non-essential storage or tracking and make refusal and withdrawal as easy as acceptance. | ePrivacy rules, EDPB consent guidance | Non-essential technology is blocked before consent, choices are granular, and withdrawal works. | Non-essential tracking starts before consent or refusal is harder than acceptance. |
| DOC-12 | Decide how minors may participate and document parental or guardian handling where required. | GDPR Article 8, local legal review | The age approach, organiser process, public-name rules, and escalation route are approved and published where relevant. | Children’s data may be published without an approved process. |
| DOC-13 | Maintain an incident and personal-data breach procedure with notification decisions and a 72-hour regulator timeline. | GDPR Articles 33–34, incident tabletop | Contacts, severity rules, evidence preservation, notification templates, and one completed tabletop test exist. | The team cannot assess, contain, document, or notify a breach on time. |
| DOC-14 | Maintain a backup, export, restore, and rollback procedure for Firestore data and Hosting releases. | Firebase backup/export documentation, restore drill | Recovery ownership, frequency, storage, access, retention, and a successful restore or rollback test are evidenced. | Backups are absent, unreadable, unprotected, or have never been restored. |
| DOC-15 | Publish terms or community rules covering acceptable use, result disputes, organiser responsibilities, and account suspension. | Product/legal review | Rules are accessible, versioned, dated, and match actual moderation capabilities. | Enforcement occurs under unpublished or inaccurate rules. |
| DOC-16 | Document intellectual-property permissions for card images, logos, names, and fan-site branding. | Asset license review, Bandai guidelines where applicable | Every non-original asset has source, permission or license, attribution, and takedown contact. | Any asset has unknown rights, missing attribution, or misleading official branding. |
| DOC-17 | Ship third-party software notices required by dependency licenses. | `license-checker` or `licensee`, package manifests | All distributed dependencies are license-compatible and required notices are included. | A prohibited, unknown, or notice-requiring license is unresolved. |
| DOC-18 | Publish an accessibility statement with conformance target, known limitations, contact, and review date. | WCAG 2.2, W3C accessibility-statement guidance | The statement is reachable and accurately reflects the tested release. | The statement is absent, stale, or claims unsupported conformance. |
| DOC-19 | Keep an operations runbook for deploy, rollback, Firebase access, custom domain, DNS, quota exhaustion, and account recovery. | Release drill, least-privilege review | A second authorized maintainer can deploy and roll back using the runbook without undocumented knowledge. | Production recovery depends on one person or undocumented credentials. |
| DOC-20 | Record release scope, commit, approvals, migrations, tests, known limitations, and rollback target. | Release checklist, changelog | The release record is complete and signed before deployment. | The deployed version cannot be tied to reviewed code and evidence. |
| DOC-21 | Review privileged accounts and role assignments before launch and on a fixed schedule. | Firebase IAM review, application role export | Every privileged identity is named, justified, protected with MFA where available, and recently reviewed. | An orphaned, shared, excessive, or unreviewed privileged account exists. |
| DOC-22 | Complete and record a DPIA screening and full assessment when high-risk processing triggers it. | GDPR Article 35, supervisory-authority guidance | Screening is approved; if triggered, the DPIA and mitigations are complete before processing. | High-risk processing launches without a completed DPIA or documented screening. |

## 3. Performance & SEO Basics

| ID | Check | Standard or tool | Pass | Fail |
| --- | --- | --- | --- | --- |
| PERF-01 | Produce a clean, reproducible production build from a fresh dependency install. | `npm ci`, `npm run build` | Both commands exit zero with the locked versions and no TypeScript or bundler error. | Installation or build fails, changes the lockfile unexpectedly, or requires an undocumented local file. |
| PERF-02 | Smoke-test the deployed release rather than only the local preview. | Playwright against production, browser console/network panels | Public routes, deep links, login, logout, and authorized workflows complete with no uncaught error or failed required request. | Any critical path fails or relies on local-only behavior. |
| PERF-03 | Meet Core Web Vitals at the 75th percentile for mobile and desktop traffic. | Chrome UX Report, PageSpeed Insights, web-vitals | LCP ≤ 2.5 s, INP ≤ 200 ms, and CLS ≤ 0.1 for at least 75% of visits. | Any metric exceeds its threshold without an approved launch exception and remediation date. |
| PERF-04 | Meet the agreed Lighthouse laboratory baseline on representative public pages. | Lighthouse CI, Chrome DevTools | Mobile Performance, Accessibility, Best Practices, and SEO scores are each at least 90 with no failing critical audit. | A score is below 90 or a critical audit fails without an approved exception. |
| PERF-05 | Enforce an initial-route transfer and bundle budget and block unexplained regressions. | Vite build report, Lighthouse resource summary | Compressed initial JavaScript stays within the approved 350 kB budget and no release grows a route by more than 10% without review. | The budget is exceeded or a regression has no owner and explanation. |
| PERF-06 | Optimize images for their rendered size and avoid unnecessary full-resolution downloads. | Lighthouse, image-size report, browser Network panel | Images use suitable dimensions and format, preserve aspect ratio, and have no material oversized-image warning. | Large off-screen or over-dimensioned images dominate transfer or layout time. |
| PERF-07 | Lazy-load non-critical images and code while keeping the primary hero content discoverable. | Browser Network waterfall, React bundle analyzer | Below-the-fold images and optional routes load on demand without delaying LCP or breaking navigation. | Non-critical assets load eagerly or lazy loading hides essential content from users or crawlers. |
| PERF-08 | Serve immutable hashed assets with long caching and HTML with a revalidation-safe policy. | `curl -I`, Firebase Hosting headers | Hashed assets use one-year immutable caching and HTML cannot remain stale across releases. | Static assets lack caching or `index.html` can pin an obsolete build. |
| PERF-09 | Confirm text assets are compressed and use correct MIME types. | WebPageTest, `curl --compressed -I` | HTML, CSS, and JavaScript receive Brotli or gzip where supported and correct content types with `nosniff`. | Large text is uncompressed or a MIME mismatch blocks or weakens protection. |
| PERF-10 | Test loading, filtering, and navigation on a throttled mid-tier mobile profile. | Chrome DevTools Slow 4G and CPU throttling, WebPageTest | Primary content appears, controls respond, and no task blocks the main thread for an unacceptable interval under the agreed profile. | The page appears frozen, drops input, or cannot complete a core journey. |
| PERF-11 | Eliminate unexpected console errors and required-resource failures. | Playwright page-error listener, browser console/network panels | Tested routes produce zero uncaught exceptions and zero failed required requests. | Any unexplained exception, CORS failure, 4xx, or 5xx affects required behavior. |
| PERF-12 | Give every indexable page a descriptive and unique title and meta description. | Lighthouse SEO, Search Console URL Inspection, crawler | Each public route has one relevant title and description in the indexed language. | Metadata is missing, duplicated, mojibake, misleading, or generic. |
| PERF-13 | Declare a stable canonical URL for every indexable page. | HTML inspection, Google Search Central canonical guidance | Each page exposes one absolute canonical matching the preferred HTTPS URL and redirect policy. | Canonicals are missing, conflicting, relative when unsupported, or point to the wrong page. |
| PERF-14 | Publish a correct `robots.txt` and XML sitemap for public canonical routes. | Google Search Console, robots.txt tester, XML validator | Production allows intended pages, blocks sensitive/non-indexable routes, and the sitemap contains only live canonical URLs. | Important pages are blocked, private routes are advertised, or sitemap URLs fail. |
| PERF-15 | Confirm search engines can render meaningful public content without authentication. | Search Console URL Inspection live test, rendered HTML snapshot | Rendered output contains headings, event content, links, and metadata without sign-in or blocked resources. | Crawlers receive an empty shell, endless loading state, blocked data, or an authentication wall. |
| PERF-16 | Return correct behavior for missing pages, retired URLs, and redirects. | `curl -I`, crawler, Firebase Hosting tests | Retired URLs redirect once to the closest replacement and missing content presents a clear not-found state with an indexing strategy documented for the SPA. | Broken URLs loop, silently show unrelated content, or create soft-404 ambiguity without a documented tradeoff. |
| PERF-17 | Use semantic heading order and descriptive internal-link text. | axe, heading outline, crawler | Each view has one clear level-one heading, logical subheadings, and links that make sense out of context. | Heading levels are skipped for styling or links use ambiguous repeated labels without context. |
| PERF-18 | Add valid structured data only where it truthfully represents visible content. | Schema.org, Google Rich Results Test | Markup validates, matches visible event or organization data, and uses supported properties. | Markup is invalid, hidden, misleading, or copied across unrelated pages. |
| PERF-19 | Provide tested Open Graph and social-card metadata for shared public pages. | Facebook Sharing Debugger, LinkedIn Post Inspector, social preview test | Title, description, canonical URL, and accessible preview image render correctly on target platforms. | Shared links show broken, stale, private, or misleading previews. |
| PERF-20 | Give each indexable language version a stable URL strategy. | Google Search Central internationalization guidance | Localized indexable pages have distinct URLs, correct language metadata and `hreflang`, or only one documented canonical language is indexed. | Language changes only in client storage while multiple languages are claimed as independently indexable. |
| PERF-21 | Verify responsive layout and content at supported viewport widths. | Playwright device projects, Chrome responsive mode | No required content clips or causes horizontal scrolling from 320 CSS px through supported desktop widths. | Text, tables, dialogs, or controls become unreachable at a supported width. |
| PERF-22 | Crawl production for broken internal links, images, and orphaned public pages. | Screaming Frog, SiteOne Crawler, link checker | All intended internal resources resolve and every public page is reachable from navigation or the sitemap. | A required resource fails or an intended page has no discoverable path. |
| PERF-23 | Monitor uptime, client errors, quota usage, and release health with an actionable owner. | Firebase dashboards, uptime monitor, error monitor | Alerts cover availability and quota thresholds, route to a named owner, and have been test-fired. | Production can fail or exhaust quota without timely detection. |
| PERF-24 | Verify the production page has no encoding corruption in Lithuanian or English content. | UTF-8 response/header inspection, visual and automated text assertions | Diacritics, punctuation, symbols, and metadata render correctly across all supported browsers. | Any mojibake or replacement character appears in visible content, metadata, or shared previews. |

## 4. Accessibility (a11y) & Usability

| ID | Check | Standard or tool | Pass | Fail |
| --- | --- | --- | --- | --- |
| A11Y-01 | Target and test WCAG 2.2 Level AA across every representative template and state. | WCAG 2.2, WCAG-EM | All Level A and AA success criteria are met or a documented blocker has an approved remediation before launch. | Any applicable A or AA criterion fails without an approved release decision. |
| A11Y-02 | Run automated accessibility scans on every representative route and role state. | axe-core or Accessibility Insights, Playwright | Automated scans report zero critical or serious violations and all moderate findings are reviewed. | A critical or serious violation remains or a route/state is untested. |
| A11Y-03 | Complete every interaction using only a keyboard. | WCAG 2.1.1 and 2.1.2, manual Tab/Shift+Tab/Enter/Space/Escape test | All controls, menus, forms, tables, login, and admin workflows are operable with no trap. | Any action requires a pointer or focus becomes trapped. |
| A11Y-04 | Keep focus order logical and move focus deliberately after navigation, dialogs, and dynamic changes. | WCAG 2.4.3, screen-reader and keyboard test | Focus follows visual/reading order and lands at the expected destination after context changes. | Focus jumps unpredictably, disappears, or remains on removed content. |
| A11Y-05 | Show a visible focus indicator that is not obscured by sticky content. | WCAG 2.4.7 and 2.4.11 | Every focusable control has a clearly visible indicator and remains at least partly visible. | Focus is hidden, clipped, removed, or indistinguishable. |
| A11Y-06 | Provide a working skip link and meaningful landmarks. | WCAG 2.4.1, Accessibility Tree inspection | The first keyboard action reveals a skip link that moves focus to main content, with unique header, navigation, main, and footer landmarks. | Repeated content cannot be bypassed or landmarks are missing/duplicated incorrectly. |
| A11Y-07 | Give every informative image equivalent alternative text and hide decorative images. | WCAG 1.1.1, axe, screen-reader test | Informative images have concise useful alternatives and decorative images use empty alternatives or CSS. | An image has missing, filename-only, duplicated, or misleading alternative text. |
| A11Y-08 | Meet text and non-text contrast in both light and dark themes. | WCAG 1.4.3 and 1.4.11, Colour Contrast Analyser | Normal text is at least 4.5:1, large text at least 3:1, and essential controls/focus graphics at least 3:1. | Any required foreground, state, border, icon, or focus indicator misses its ratio. |
| A11Y-09 | Never use color alone to communicate leader color, status, selection, error, or ranking. | WCAG 1.4.1, grayscale/manual review | Every color-coded meaning also has text, iconography, pattern, or programmatic state. | Meaning is lost when color is unavailable. |
| A11Y-10 | Support 200% text zoom and 400% page zoom/reflow without loss of content or function. | WCAG 1.4.4 and 1.4.10, browser zoom at 1280 CSS px | Content reflows to the equivalent 320 CSS px width without two-dimensional scrolling except allowed data tables. | Text clips, overlaps, disappears, or controls become unusable. |
| A11Y-11 | Preserve content and function when users override text spacing. | WCAG 1.4.12, text-spacing bookmarklet | Required line, paragraph, letter, and word spacing can be applied without clipping or loss. | Content or controls break under the WCAG text-spacing values. |
| A11Y-12 | Associate every input with a persistent label, instructions, and required-state information. | WCAG 1.3.1 and 3.3.2, axe, Accessibility Tree | Each field exposes an accessible name and any format, limit, or requirement before entry. | A placeholder is the only label or instructions are unavailable to assistive technology. |
| A11Y-13 | Identify validation errors in text, connect them to fields, and preserve entered values. | WCAG 3.3.1 and 3.3.3, invalid-form tests | Submission names each error, moves or announces focus appropriately, and suggests a correction where known. | Errors rely on color, are generic, erase data, or are not announced. |
| A11Y-14 | Announce loading, save success, authentication failure, and other status updates without stealing focus. | WCAG 4.1.3, screen-reader test | Status regions announce concise updates once and users can continue their task. | Important updates are silent, repeated excessively, or unexpectedly move focus. |
| A11Y-15 | Ensure every control exposes the correct accessible name, role, value, and state. | WCAG 4.1.2, Accessibility Tree, axe | Native controls or valid ARIA expose labels plus expanded, selected, disabled, or checked state as applicable. | A control is unnamed, has the wrong role, or hides its current state. |
| A11Y-16 | Make visible control text part of the control’s accessible name. | WCAG 2.5.3 | Speech users can activate controls using their visible labels. | The accessible name conflicts with or omits the visible label. |
| A11Y-17 | Provide pointer targets at least 24 by 24 CSS pixels or sufficient spacing. | WCAG 2.5.8, browser measurement | Every pointer target meets the size or spacing exception and adjacent targets are not easily mis-hit. | A small crowded target has no valid exception. |
| A11Y-18 | Support portrait and landscape orientation without restricting the interface. | WCAG 1.3.4, mobile device test | All essential content and functions work in both orientations. | Orientation is locked or a function disappears in one orientation. |
| A11Y-19 | Respect reduced-motion preferences and avoid flashing or unnecessary motion. | WCAG 2.3.1 and 2.3.3, `prefers-reduced-motion` test | No content flashes above the threshold and non-essential animation is disabled or reduced on request. | Flashing risks seizures or motion cannot be reduced. |
| A11Y-20 | Mark page language and language changes correctly. | WCAG 3.1.1 and 3.1.2, HTML/Accessibility Tree inspection | The root `lang` matches the active language and foreign-language passages that need it are marked. | Screen readers receive the wrong language or mixed-language content is unmarked. |
| A11Y-21 | Give data tables proper headers, captions or nearby context, and a usable small-screen presentation. | WCAG 1.3.1, screen-reader table navigation | Header associations are announced correctly and users can reach every cell at zoom and mobile widths. | Tables are visually formatted without semantic headers or become inaccessible on small screens. |
| A11Y-22 | Make authentication usable without memory, transcription, puzzle, or password barriers. | WCAG 3.3.8, Google Sign-In accessibility test | Google authentication completes with assistive technology and offers an accessible recovery/escalation path. | Authentication introduces an inaccessible cognitive-function test or blocks assistive technology. |
| A11Y-23 | Test representative journeys with NVDA or VoiceOver in addition to automated scanning. | NVDA + Chrome/Firefox, VoiceOver + Safari | Navigation, filters, tournament results, login, role management, event editing, errors, and status messages are understandable and operable. | A critical journey is confusing, silent, or blocked in either agreed screen-reader/browser pair. |
| A11Y-24 | Keep navigation, labels, icons, and interaction patterns consistent across routes and languages. | WCAG 3.2.3 and 3.2.4, heuristic review | Repeated controls retain location, name, icon meaning, and behavior unless a change is explained. | Identical actions use conflicting labels or behavior. |
| UX-01 | Complete end-to-end acceptance tests for Visitor, Organiser, Editor, Administrator, and Owner. | Playwright, role-based test accounts | Every role completes allowed journeys and receives a clear denial for prohibited journeys. | A required journey fails or a prohibited action appears successful. |
| UX-02 | Verify loading, empty, error, offline, quota-exceeded, and retry states on every data-driven view. | Network throttling/offline mode, forced Firebase errors | Each state explains what happened, preserves context where safe, and provides a working next action. | The interface hangs, goes blank, loses work, or shows raw technical errors. |
| UX-03 | Prevent duplicate submissions and communicate save progress and completion. | Slow-network interaction test | Submit controls disable or deduplicate while saving and exactly one record is created. | Double clicks create duplicates or users cannot tell whether a save completed. |
| UX-04 | Validate destructive or irreversible actions with confirmation and recovery appropriate to impact. | Heuristic review, workflow test | High-impact actions state the target and consequence and offer undo or explicit confirmation where feasible. | A single accidental action can cause unannounced permanent loss. |
| UX-05 | Preserve user input after recoverable validation, authentication, or network failure. | Form failure tests | Correct values remain and only fields needing correction require re-entry. | A recoverable error clears the form or forces unnecessary re-entry. |
| UX-06 | Verify supported browsers and devices with the published support matrix. | BrowserStack or physical devices, Playwright | Latest Chrome, Firefox, Edge, Safari, and agreed mobile browsers complete all critical public journeys. | A supported browser has a blocking functional or layout defect. |
| UX-07 | Review Lithuanian and English copy for accuracy, completeness, truncation, and consistent terminology. | Native-speaker review, visual regression | Every user-visible string is translated correctly and fits at supported widths. | Mixed languages, missing keys, mojibake, misleading copy, or truncation appears. |
| UX-08 | Make contact, privacy, accessibility, and issue-reporting paths easy to find. | Navigation and footer review | Users can reach each published support or policy page within two interactions from any public page. | A user cannot find how to ask for help, report a problem, or exercise privacy rights. |

## Required release evidence

| Field | Required value |
| --- | --- |
| Release | Version or commit SHA |
| Candidate URL | Exact HTTPS URL tested |
| Test window | Start and finish timestamp in UTC |
| Testers | Named technical, content, privacy, and accessibility reviewers |
| Automated reports | Build, unit, browser, rules, dependency, Lighthouse, axe, and ZAP artifacts |
| Manual evidence | Role matrix, keyboard, screen reader, localization, privacy, restore, and rollback results |
| Exceptions | Gate ID, risk, owner, approver, expiry date, and remediation issue |
| Decision | `GO` only when every applicable row passes and every exception is explicitly accepted |

## Project commands

```powershell
npm.cmd ci
npm.cmd audit --omit=dev --audit-level=high
npm.cmd test
npm.cmd run build
npm.cmd run test:browser
npm.cmd run test:rules
```

Run browser tests against the deployed release candidate as a separate pass. Store generated reports outside Git unless they are intentionally attached to a release record.
